# bastau ai — Autopilot: генерация и продажа сайтов на автопилоте

> Документ-задание для всей команды. Часть для парсера и WhatsApp-рассылки — зона ответственности **разработчика №2 (парсер + рассылка)**. Части CRM и ИИ-агентов — зона разработчика №1. Этот файл можно целиком скормить ИИ-ассистенту для планирования и кода.

---

## 1. Идея проекта

Мы находим бизнесы **без сайта**, автоматически выходим на них в WhatsApp, ИИ-продажник ведёт переписку, при согласии второй ИИ-агент **сам генерирует готовый сайт** и деплоит его, а первый агент отправляет клиенту **живую ссылку на демо-версию**. Клиент видит готовый результат ещё до оплаты.

Переворот воронки: мы не продаём услугу «сделаем сайт», мы показываем **уже сделанный сайт** — «вот ваша демо-версия, что поправить?».

**Весь процесс автоматический.** Ручное вмешательство только на этапе правок, после того как клиент посмотрел демо.

---

## 2. Роли в команде

| Кто | Зона ответственности |
|---|---|
| **Разработчик №2** | Парсер лидов (бизнесы без сайта) + WhatsApp-рассылка первого касания. Пишет лиды в CRM. |
| **Разработчик №1** | CRM (Supabase) + ИИ-агент №1 (продажник) + ИИ-агент №2 (сайт-билдер на Claude) + оркестрация. |

Граница между зонами — **CRM**. Обе стороны общаются только через неё, напрямую сервисы друг друга не дёргают.

---

## 3. Архитектура и поток данных

```
[Парсер]  →  лид (бизнес без сайта)  →  CRM (status: NEW)          ← зона Разработчика №2
    │
[WhatsApp-рассылка первого касания]  →  CRM (status: CONTACTED)     ← зона Разработчика №2
    │
клиент ответил в WhatsApp
    ▼
[ИИ-агент №1 «Продажник»]  диалог, квалификация, сбор брифа         ← зона Разработчика №1
    → CRM (status: IN_DIALOG → QUALIFIED, + brief)
    │
    ▼
[ИИ-агент №2 «Сайт-билдер» + Claude]  бриф → сайт → деплой          ← зона Разработчика №1
    → CRM (status: SITE_READY, + site_url)
    │
    ▼
[ИИ-агент №1] видит SITE_READY → шлёт клиенту ссылку в WhatsApp     ← зона Разработчика №1
    → CRM (status: SENT)
    │
    ▼
клиент смотрит демо → правки → РУЧНОЕ вмешательство (менеджер)
```

**Главный принцип:** CRM — это шина сообщений. Каждый компонент реагирует на смену `status` лида и меняет `status` дальше. Никто ни с кем не общается напрямую.

## 4. CRM — контракт данных (это интеграционная граница!)

CRM = **Supabase** (Postgres + REST API + Realtime + Webhooks). Разработчик №1 поднимает базу и даёт Разработчику №2 доступ на запись в таблицу `leads`.

### Таблица `leads`

| поле | тип | кто заполняет | описание |
|---|---|---|---|
| `id` | uuid (auto) | — | первичный ключ |
| `business_name` | text | **парсер** | название бизнеса |
| `category` | text | **парсер** | сфера (барбершоп, кафе, автосервис…) |
| `phone` | text | **парсер** | телефон в формате `77001234567` (без +, без пробелов) |
| `whatsapp` | text | **парсер** | номер WhatsApp, если отличается |
| `city` | text | **парсер** | город |
| `address` | text | **парсер** | адрес (если есть) |
| `source` | text | **парсер** | откуда лид: `2gis` / `google_maps` / `instagram` |
| `source_url` | text | **парсер** | ссылка на карточку-источник |
| `has_site` | bool | **парсер** | должно быть `false` (фильтр: только без сайта) |
| `status` | text (enum) | все компоненты | текущий статус (см. ниже) |
| `conversation` | jsonb | агент №1 | история переписки |
| `brief` | jsonb | агент №1 | собранный бриф на сайт |
| `site_prompt` | text | агент №2 | итоговое ТЗ для генерации |
| `site_url` | text | агент №2 | ссылка на демо-сайт |
| `created_at` | timestamp (auto) | — | |
| `updated_at` | timestamp (auto) | — | |

### Статусы (конечный автомат)

```
NEW → CONTACTED → IN_DIALOG → QUALIFIED → BUILDING → SITE_READY → SENT → REVISION → WON / LOST
```

**Что делает разработчик №2 со статусами:**
- Парсер создаёт лид со статусом **`NEW`**.
- После отправки первого сообщения рассылкой — ставит статус **`CONTACTED`**.
- Дальше в статусы не лезет — их ведут ИИ-агенты.

### Как парсер пишет лид (пример REST-запроса к Supabase)

```http
POST https://<project>.supabase.co/rest/v1/leads
apikey: <SERVICE_KEY>
Authorization: Bearer <SERVICE_KEY>
Content-Type: application/json

{
  "business_name": "Барбершоп Alpha",
  "category": "барбершоп",
  "phone": "77001234567",
  "whatsapp": "77001234567",
  "city": "Астана",
  "address": "пр. Кабанбай батыра 15",
  "source": "2gis",
  "source_url": "https://2gis.kz/...",
  "has_site": false,
  "status": "NEW"
}
```

### Обновление статуса после рассылки

```http
PATCH https://<project>.supabase.co/rest/v1/leads?id=eq.<lead_id>
{ "status": "CONTACTED" }
```

> Разработчик №1 заранее пришлёт `<project>` URL и `<SERVICE_KEY>`. До этого парсер можно писать в CSV в этом же формате колонок, потом импортировать.

## 5. Зона Разработчика №2 — детально

### 5.1. Парсер лидов

**Задача:** собрать бизнесы, у которых **нет сайта**, с контактным WhatsApp/телефоном.

**Источники (Казахстан):**
- **2ГИС** — основной. В карточке есть телефон, категория, адрес; поле сайта отсутствует = лид подходит.
- **Google Maps** — дополнительный (Places API или парсинг выдачи).
- **Instagram** — бизнес-профили без ссылки на сайт, но с WhatsApp-кнопкой.

**Логика фильтра «нет сайта»:** в карточке нет поля Website / ссылки на домен, но есть телефон или WhatsApp.

**Что важно на выходе:**
- Телефон в едином формате `77XXXXXXXXX` (нормализация обязательна).
- Дедупликация по `phone` (один бизнес — один лид).
- Проверка, что номер реально в WhatsApp (по возможности — через статус в GREEN-API `checkWhatsapp`).

**Стек (на выбор):** Python + requests/Playwright для 2ГИС; готовые парсеры Google Maps; аккуратно с частотой запросов, чтобы не ловить блок.

### 5.2. WhatsApp-рассылка первого касания

**Задача:** отправить каждому лиду **первое** персонализированное сообщение, после которого дальнейший диалог подхватывает ИИ-агент №1.

#### ⚠️ ГЛАВНЫЙ РИСК ПРОЕКТА — читать обязательно

Массовая **холодная** рассылка в WhatsApp нарушает правила WhatsApp и ведёт к **бану номера** (иногда за часы). Это ограничение платформы, его нельзя «обойти кодом». Поэтому:

- **НЕ** гнать тысячи сообщений с одного нового номера.
- Использовать **прогретые** номера, начинать с малых объёмов (10–30 сообщений/день на номер), плавно наращивать.
- Разные тексты (не один шаблон на всех), задержки между сообщениями, «человеческий» ритм.
- Держать несколько номеров и раскидывать нагрузку.
- Идеально — **полуавтомат на первом касании**: генерируем персональные `wa.me`-ссылки с готовым текстом, отправку инициирует человек/скрипт малыми партиями. Дальше, когда клиент **ответил**, диалог 1-на-1 ведёт агент — это уже безопасно.

#### Технический канал: GREEN-API (или Wazzup24)

Для КЗ/СНГ берём **GREEN-API** — REST-обёртка над WhatsApp:
- **Отправка:** `POST /sendMessage` с `chatId` (`77001234567@c.us`) и `message`.
- **Приём входящих:** webhook — GREEN-API дёргает наш URL при каждом входящем сообщении.
- **Проверка номера в WhatsApp:** `checkWhatsapp`.

Каждый рабочий WhatsApp-номер = отдельный инстанс GREEN-API.

#### Шаблон первого сообщения (пример)

```
Здравствуйте! Вижу, у «{business_name}» пока нет сайта.
Мы в bastau ai делаем сайты для бизнеса. Хотите, бесплатно
покажу, как мог бы выглядеть сайт вашего {category}? Пришлю ссылку 🙌
```

Текст должен варьироваться, обращаться по названию бизнеса и категории (данные из лида).

#### Что происходит после первого касания

1. Парсер/рассылка ставит лиду `status = CONTACTED`.
2. Клиент отвечает → GREEN-API шлёт webhook.
3. **Внимание, точка стыковки:** входящие сообщения должен обрабатывать **ИИ-агент №1 (зона Разработчика №1)**. Поэтому webhook GREEN-API рабочих номеров нужно направить на эндпоинт агента №1. Договоритесь, кто держит инстансы GREEN-API:
   - **Рекомендуемо:** инстансы GREEN-API оформлены так, что их webhook на входящие идёт сразу на сервис Разработчика №1. Разработчик №2 использует эти же инстансы только для исходящей рассылки.
   - Итог: один канал (номер) — рассылку шлёт №2, ответы принимает агент №1.

## 6. Зона Разработчика №1 (кратко — для понимания стыка)

- **CRM (Supabase):** таблица `leads`, статусы, вебхуки на смену `status`.
- **Агент №1 «Продажник»:** принимает входящие WhatsApp (webhook GREEN-API), ведёт диалог через Claude, собирает `brief`, при согласии ставит `QUALIFIED`. Когда лид становится `SITE_READY` — шлёт клиенту `site_url`, ставит `SENT`.
- **Агент №2 «Сайт-билдер»:** триггер на `QUALIFIED`, превращает `brief` в сайт через Claude, деплоит (Netlify/Vercel), пишет `site_url`, ставит `SITE_READY`.

Разработчику №2 внутренности агентов знать не нужно — важен только **контракт CRM** из раздела 4 и **стыковка webhook** из раздела 5.2.

## 7. Что нужно согласовать между разработчиками

1. **Supabase:** №1 создаёт проект, отдаёт №2 URL + ключ на запись в `leads`.
2. **Формат телефона:** единый `77XXXXXXXXX` — договорённость жёсткая.
3. **GREEN-API инстансы:** кто заводит номера, куда направлен webhook входящих (на агента №1).
4. **Объёмы рассылки:** согласовать безопасный дневной лимит на номер (старт: 10–30/день на прогретый номер).
5. **Схема `brief`** (её собирает агент №1, но полезно, чтобы №2 понимал, какие данные о бизнесе ценны — их можно тащить и парсером):
```json
{
  "business_type": "барбершоп",
  "goal": "запись клиентов",
  "pages": ["главная", "услуги", "контакты"],
  "style": "тёмный, премиум",
  "services": ["стрижка", "оформление бороды"],
  "contacts": { "whatsapp": "77001234567", "address": "..." },
  "agreed": true
}
```

## 8. Этапы (дорожная карта)

| Этап | Разработчик №2 | Разработчик №1 |
|---|---|---|
| 1 | Парсер → выгрузка лидов в CSV (формат колонок из разд. 4) | Поднять Supabase + таблицу `leads` |

| 3 | GREEN-API: отправка первого касания малыми партиями | Агент №1 (продажник) на тестовом номере |
| 4 | Прогрев номеров, тюнинг текстов, анти-бан | Склейка агентов через вебхуки статусов |
| 5 | Масштабирование рассылки (несколько номеров) | Дашборд CRM, аналитика воронки |

## 9. Итог для Разработчика №2 — три вещи, которые нужно сделать

1. **Парсер:** бизнесы без сайта → запись в CRM (`leads`, `status=NEW`) в точном формате разд. 4.
2. **Рассылка первого касания:** GREEN-API, персональный текст по данным лида, безопасные объёмы (анти-бан!), после отправки → `status=CONTACTED`.
3. **Стыковка:** входящие ответы клиентов идут на webhook агента №1 (не обрабатывать самому).

Всё остальное (диалог, генерация сайта, отправка ссылки) — на стороне Разработчика №1.
